# 一套权重 · 多角色（One-Weight Multi-Role）—— 最小验证原型

> 验证目标：**同一个模型**，根据输入里附带的**角色标识 token**（`[ROOT]` / `[LEAF]` / `[CHAT]`），
> 在同一棵"任务树"的不同位置扮演不同角色，端到端训练，误差回传同一套权重。
>
> 验证任务：① `创建一个叫 hello.txt 的文件，里面写"你好"`（ROOT/LEAF 闭环）
>           ② 把同一个模型发展成一个**简单的多轮对话模型**（CHAT 角色）

这是一个**原型验证（prototype）**：不追质量，只追闭环。
先把 `拆解 → 执行 → 验证 → 回传` 这条链跑通，再谈扩展。

---

## 1. 架构核心

```
                用户任务
                   │
            ┌──────▼──────┐
            │   [ROOT]    │  角色：根，负责"拆解任务"
            │  拆解子任务  │
            └──────┬──────┘
        ┌──────────┼──────────┐
        ▼          ▼          ▼
   ┌────────┐ ┌────────┐ ┌────────┐
   │[LEAF]  │ │[LEAF]  │ │[LEAF]  │  角色：叶，负责"执行原子任务"
   │执行子任│ │执行子任│ │执行子任│
   └───┬────┘ └───┬────┘ └───┬────┘
       │          │          │
       ▼          ▼          ▼
   ┌────────────────────────────┐
   │  执行器（真实 os 写文件）    │
   └─────────────┬──────────────┘
                 ▼
   ┌────────────────────────────┐
   │  验证器（真实读文件检查）    │  → 算 loss → 回传整棵树 → 更新同一套权重
   └────────────────────────────┘
```

- **一套权重**：ROOT 和 LEAF 共用同一个 `RoleLM`（一个小型因果 Transformer）。
- **角色标识 = 特殊 token**：输入里写 `[ROOT]` 或 `[LEAF]`，分词器把它当作一个独立 token。
  同一套权重，喂不同的角色 token，行为就不同——这是"多角色"的实现方式，不靠改网络结构。
- **一棵树 = 一个计算图**：ROOT 产出 N 个子任务，每个子任务喂给一个 LEAF，形成 1→N 的扇出。
- **端到端 / 误差回传**：ROOT 的 loss 与 LEAF 的 loss 反传到的是**同一组参数**，
  这就是"误差从结果回传到根"的最小体现。

- **新增 CHAT 角色（对话）**：同一个 `RoleLM`，喂入带 `[CHAT]` 角色标识的对话历史
  （格式 `[CHAT]用户：你好|助手：你好！|用户：你会做什么`），就会切换到"对话模式"产出助手回复。
  它的 loss 和 ROOT/LEAF 一起反传到**同一套权重**——所以模型现在已经能同时**拆任务、执行文件操作、聊天**，
  全靠一个参数空间 + 不同角色 token 区分。多轮对话靠把历史拼回 prompt 实现（不引入额外隐藏状态）。

## 2. 完整代码结构

| 文件 | 作用 |
|------|------|
| `config.py` | 全局配置：路径、模型超参（D=256, heads=4, layers=3, ff=512）、训练超参、随机种子。 |
| `model.py` | `RoleLM`：共享权重的小型 Transformer（GPT 风格，Pre-LN，权重共享输出层）。含 `generate`（贪心解码）、`generate_beam`（束搜索解码，推理用）与 `count_params`。 |
| `data.py` | 自造训练数据（**任务样本 + 对话样本**两类，共用一个词表）+ 字符级分词器（特殊 token 整体处理）+ `parse_subtasks` + 对话工具 `build_chat_samples` / `format_chat` / `chat_pair`。 |
| `executor.py` | **执行器**：真的调用 `os` 写文件。`TOUCH <文件>` 建空文件，`WRITE <文件> <内容>` 写内容（支持中文）。 |
| `validator.py` | **验证器**：真的读文件，检查是否存在、内容是否匹配，返回 `exists/match/score`。 |
| `pipeline.py` | 推理流水线：`run_pipeline`（ROOT 拆解 → LEAF 执行 → 执行器写文件 → 验证器检查）+ `run_chat_turn`（多轮对话，把历史拼回 prompt 用 beam 解码）。**推理用束搜索（beam）解码**，纠正字符级生成的偶发单字错误。 |
| `train.py` | **训练脚本**：ROOT / LEAF / CHAT 三类样本的 LM loss 一起反传到同一套权重 + 子集上的"真实执行环"（真写真验证，监控 + 落盘）。每 5 轮清空沙箱用 beam 跑演示任务，通过才存 `model.pt`。 |
| `infer.py` | **推理脚本**：对给定任务跑完整条链并打印每一步。默认跑演示任务。 |
| `chat.py` | **对话脚本（新增）**：交互式多轮对话（`python chat.py`）或单句问答（`python chat.py "你会做什么"`）。 |
| `validate.py` | **验证脚本**：双轨硬验证——① 文件任务（hello.txt 是否被真实创建且内容正确）② 对话冒烟（问预设问题 + 一段多轮是否连贯），给出 PASS/FAIL 与退出码。 |
| `requirements.txt` | 依赖：`torch>=2.0`。 |

> 一条训练样本的结构（满足 `任务 → 拆解 → 执行结果`）：
> ```json
> {
>   "task":     "创建文件hello.txt并写入内容你好",
>   "decomp":   "子任务1:创建文件hello.txt;子任务2:向hello.txt写入内容你好",
>   "subtasks": ["创建文件hello.txt", "向hello.txt写入内容你好"],
>   "actions":  ["TOUCH hello.txt", "WRITE hello.txt 你好"]
> }
> ```

## 3. 训练和运行命令

```bash
# 0) 安装依赖（CPU 即可）
pip install -r requirements.txt

# 1) 训练：会生成 data.json（合成数据）并训练，保存 model.pt
python train.py
#    想快速试跑可调小轮数： TRAIN_EPOCHS=5 python train.py

# 2) 推理：跑完整条链并打印拆解 / 子任务 / 动作 / 执行 / 验证
python infer.py
#    也可指定其它任务： python infer.py "创建文件foo.txt并写入内容世界"

# 3) 验证：双轨硬验证（文件闭环 + 对话冒烟）
python validate.py

# 4) 对话：交互式多轮对话（输入 exit 退出）
python chat.py
#    或单句问答： python chat.py "你会做什么"
```

- 真实文件写在 `./sandbox/` 目录下（由 `WORK_DIR` 控制）。
- 训练数据约 **570 条**（任务样本 ~320 + 对话样本 ~250）、词表约 **208**、模型参数量约 **1.66M**（在 1M–10M 区间，CPU 可跑）。

## 4. 预期结果（实测）

一次 80 轮训练（CPU，约 40 分钟）的实测曲线（`train.log`）：

| epoch | loss | task_loss | chat_loss | real_acc |
|-------|------|-----------|-----------|----------|
| 1     | ~17  | ~21       | ~12.7     | 0.00     |
| 5     | ~2.1 | ~2.0      | ~1.1      | 0.00→0.5 |
| 15    | ~0.5 | ~0.33     | ~0.33     | 0.6      |
| 25    | ~0.40| ~0.19     | ~0.39     | 1.00 ✅  |
| 80    | ~0.27| ~0.17     | ~0.25     | 0.8~1.0  |

- **loss 稳定下降**：`loss` 从 ~17 一路降到 ~0.27，任务/对话两类 loss 同步收敛。
- **real_acc 上升并触顶**：子集真实执行环的 `real_acc` 在训练中段就达到 **1.000**（文件创建+内容正确）。
- **文件真的被创建**：训练过程中 `./sandbox/` 真实出现 `hello.txt` 等文件；`python validate.py` 输出 `PASS ✅`，且 `./sandbox/hello.txt` 内容为 `你好`。
- **model.pt 是最佳检查点**：训练每 5 轮（及末轮）会**先清空沙箱**再用 beam 跑一次演示任务，只有 `hello.txt` 内容确实等于 `你好` 才把权重保存为 `model.pt`。因此交付的 `model.pt` 是一个"演示任务通过"的版本，可直接用 `validate.py` 复现成功。
- **角色生效**：`infer.py` 里同一个模型，喂 `[ROOT]...` 输出"拆解"，喂 `[LEAF]...` 输出"执行动作"，
  证明多角色由同一套权重 + 角色 token 实现。
- **对话可用**：`chat.py` 里同一个模型，喂 `[CHAT]用户：你好...` 会输出"你好！..."之类的问候/应答；
  多轮时把历史拼回 prompt，模型能接上上下文（如先问"你好"再问"你是谁"，第二轮仍给出连贯应答）。
  这证明 `[CHAT]` 与 `[ROOT]`/`[LEAF]` 共享同一套权重，只是角色 token 不同。

## 5. 已知局限（重要，原型边界）

1. **不能对 `os` 写文件求导**：文件 IO 是不可导的副作用，梯度无法真正"穿过" `os.write`。
   本原型用**教师强制的语言模型 loss** 作为可导的梯度载体（它天然逼迫模型产出能让验证器通过的动作），
   同时把**真实执行器 + 真实验证器**跑在环里，证明系统在世界中真的闭环。
   `loss = root_loss + leaf_loss + ALPHA * (1 - real_acc)` 中 `real_acc` 仅作辅助/监控信号（detached）。
   要做"真正从环境奖励端到端反传"，需要可微环境或 neuro-symbolic 桥接（见下）。

2. **训练时用真值子任务喂 LEAF**：为了让训练稳定且快速，LEAF 的教师强制目标用的是规范子任务；
   "模型自己拆解 → 喂 LEAF"的闭环在 `pipeline.py` / `infer.py` / `validate.py` 的真实执行环里演示。

3. **数据靠规则合成、字符级、模板化**：仅为验证架构闭环，不具备泛化能力；换个没见过的文件名/内容格式可能失效。

4. **推理用 beam 解码，但训练仍是教师强制；未引入 RL**：原型追求最快跑通，没有用 REINFORCE/PPO 等把稀疏奖励直接反传到权重。beam 仅用于推理时纠正字符级生成的偶发单字错误。

5. **对话是"模板记忆式"，不是真实语义理解**：`[CHAT]` 角色靠教师强制 LM loss 学习训练过的问答模式，
   超出训练分布的问题（如复杂推理、知识问答）回答可能发散或重复 prompt。多轮靠"把历史拼回 prompt"实现，
   没有长期记忆 / 注意力之外的状态。这是原型"追闭环、不追质量"定位下的预期行为。

## 6. 后续可扩展方向（先闭环，后扩展）

- **可微环境**：用一个可微的"文件世界"模拟器（如把文件内容做成稠密张量）替代真实 `os`，让验证结果能真正反传。
- **RL 闭环**：把验证器的 0/1 当作 reward，用 REINFORCE/PPO 端到端训练，角色 token 作为 policy 的条件。
- **更深树 / 动态扇出**：支持 ROOT 产出不定数量子任务、子任务再拆解（多层级树）。
- **更大词表与子词分词**：提升对未见文件名/内容的泛化。
